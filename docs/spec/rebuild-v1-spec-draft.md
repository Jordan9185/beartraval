## 0. 連貫的產品全貌

【已確認規格】新版是由 AI 助理統整的旅行工具：接收想去、想吃、想買的內容，主動查證去處並綜合旅程提出安排；使用者確認重要選擇後，能帶著同一份行程與清單出發。購買清單及旅行必備用品清單均為核心範圍。

### 0.2 同一份資料在各處接續使用

【建議】以下關係是新版連貫性設計，後續落定操作規則與資料契約：

- 原始分享 → 辨識項目：同一篇可拆出多個地點／商品，每項保留來源；不是分享一次就強迫分類一次。
- 收藏地點 → 已安排站點：排入後保留關聯與已排日期；撤回排程仍保留收藏，不要求重新分享。
- 商品 → 販售候選 → 購買安排 → 同一天的店家站點：商品不當作地點，同店多商品可關聯同一站，避免重複排店。
- 必備用品 → 需要購買 → Shopping：購買與打包各自勾選；已有物品不必建立購買項目。
- AI 建議 → 已確認正式安排 → Today：各頁引用同一安排，保留使用者確認的店家、日期、地址及商品；不產生互不相通的清單副本。
- 個人資料 → 明確選擇加入 Trip → 共同項目：AI 可以分析選定私人內容，但提出建議不等於同意公開；共享前說明範圍。

## 1. 新版原始需求與範圍

【已確認規格】原始需求與本輪補充：

- 行程：貼上文字行程 → AI 解析 → 確認地點 → 建立 Trip → Today。

【已確認規格】新版核心範圍包含行程、收藏、購買清單、旅行必備用品清單及好友共享。

【已確認規格】R6：一句話生成整趟旅行、影片／語音辨識、系統推播、計程車卡朗讀、叫車付款、獨立好友社交與即時庫存查詢列入第二版規劃／評估，不納入第一版。庫存功能需可靠資料來源，不承諾保證有貨。AI 助理統整整趟行程已納入核心，首頁與入口依 Q31–Q33；細部排版待線框圖。

【已確認規格】沿用現行硬性規則：AI 只提出建議；正式行程變更需使用者確認；AI 不可移動固定站點；不可猜分店或座標；順路為增加的旅行時間，未知不填零；收藏與商品分開；可能販售不等於有庫存；好友在指定 Trip 內新增地點預設進該 Trip 共同收藏；外部分享仍遵循個人保存與明確共享規則；服務端驗權限與版本。

## 1.1 整體 AI 助理與主動補查

【已確認規格】產品負責人指出第一版體驗不連貫：地圖查不到地點就不安排，並非期待行為。此為本輪使用者回饋，尚未在本輪重新檢查程式或重現。

【已確認規格】新版由同一個 AI 助理掌握整趟旅程。匯入想買、想吃、想去的內容後，只要目標旅程已知，就自動分析並提出日期與安排；使用者按「確認安排」才寫入正式行程。多趟旅程且無法判斷目標時才詢問，不要求使用者先逐日比較。

【已確認規格】主流程為「保存內容 → 辨識意圖 → AI 主動搜尋補查 → 綜合整趟旅行提出安排 → 使用者確認 → 正式行程／今天」。Route Match 為安排時使用的判斷能力，地圖搜尋成功及取得座標都不是提出安排的必要前提。

| ID | 已確認需求 |
|---|---|
| A1 多語店名與景點 | 輸入可為中文譯名、音譯、暱稱、原文、錯字或 OCR 結果；AI 主動以名稱及上下文搜尋並核對實際店家、分店、地區與地址，不以地圖搜尋作為前置條件。 |
| A2 特定商家商品 | AI 根據品牌、商品及型號線索，搜尋可能販售的店名與地點，提供去哪裡買的建議；商品身份或分店有歧義時再請使用者確認。 |
| A3 整體安排 | 綜合已有行程、每天區域、用餐時段、可得營業資訊、停留需求、固定事項與可得交通資料，提出哪一天、哪個位置適合加入及其理由。 |
| A4 地圖未知仍可排 | 有可核對店名、地區或地址線索但無可信座標時，仍能提出日期建議；使用者確認後建立待定位站點，保留原文店名、地址線索、來源與商品關聯。不得把安排責任全部退回使用者手動選日。 |
| A5 正式變更需確認 | AI 補查與建議不自動改正式行程；需移動原安排時清楚呈現變更，固定事項不可由 AI 移動。 |

【已確認規格】搜尋結果必須保留依據，區分已查得資料、可能販售、庫存未知與 AI 推論；不可用模型記憶冒充已搜尋，不能猜分店、座標或交通分鐘數。找得到店家不代表該分店有售特定商品，更不代表即時有貨。

【建議】三種資訊完整度採不同處理：

- 店家／分店及地址明確，座標未知：AI 仍可建議日期，說明以區域與時段判斷，交通未估算；確認後可排入待定位站點。
- 有多個合理分店／販售候選：AI 先依旅程比較並推薦，保留其他候選，使用者確認去處；不可靜默選為已確認分店。
- 只有商品或店名，沒有可靠去處線索：繼續保留想買／想去項目與查詢結果；說明缺少什麼，必要時集中詢問，不編造目的地或假裝已安排成功。

【建議】辨識、搜尋與路線查詢分開回報進度；其中一項失敗不丟失已取得資訊。座標之後補齊時重新評估交通影響，若需要改日或改順序，再提出需確認的調整，不默默改原安排。多筆匯入可彙整為一份建議，記住人工更正及拒絕結果。

【需實測或決策】搜尋工具與資料來源、可存取範圍、查詢時效、背景執行與等待時間於技術規劃驗證；本文件未宣稱現有 AI 已具備可靠搜尋能力。新版依 §12 支援本機 GPT 訂閱與明確選擇的 Claude API；本輪未改動現行部署或地圖供應商。

【建議】新增必要驗收樣本：韓文店名地圖查無結果仍能補查並建議排日；商品圖片能補查候選販售店與來源；同名分店需確認；無座標能確認排入並在 Today 找到；沒有販售證據時保留未知；補定位後發現衝突不自動覆蓋正式行程。

## 1.2 不依賴地圖查店與跨語店家核對

【已確認規格】AI 搜尋、理解與交叉核對為店家／商品研究的主要流程，從一開始就執行，不是等地圖查詢失敗才啟動的備援。不得要求先有地圖搜尋結果、Place ID 或座標，才辨識店家、搜尋販售據點或提出排日建議。地圖查詢是可選的補充定位工具，路線與導航是後續能力。

【已確認規格】產品必須支援使用者指出的中國、韓國等地圖查詢受限情境；這是產品適用情境，不宣稱本輪已驗證各國或各地圖供應商的涵蓋率。地圖未回傳結果不等於店家不存在。

【已確認規格】使用者提供的店名可能已翻譯，不能假設輸入是當地正式名稱。應保留使用者原始名稱，結合貼文、截圖招牌、旅行目的地、街區、料理、品牌或商品線索，搜尋不同語言名稱並核對同一店家；翻譯或音譯只是搜尋線索，不是身分證據。

【已確認規格】「無垢屋」作為本輪使用者提供的中文店名範例：不能逐字翻成韓文就當成正式店名，也不能把對話中的近似字形直接當成已確認別名。本輪未查證其實際韓文名稱、地址或分店，不在規格中建立名稱對應。

【建議】AI 調查順序：

1. 保留原始輸入及來源，抽取城市、街區、照片、招牌、菜色或商品等線索。
2. 以原輸入及不同語言查詢實際來源，產生可能對應的店家；有可靠原文名稱後再用原文補查。
3. 比對地址、分店、品牌、招牌或來源連結等識別線索，不只比較名稱相似度；缺資料或來源互相矛盾時保留歧義。
4. 呈現使用者熟悉的名稱、查得的當地名稱、分店／地區、地址與來源；當地名稱未知就保留未知，不生成假的原文店名。
5. 有足夠地區及店家依據時提出排日建議；座標未知不阻擋。若候選身份尚有歧義，先推薦並讓使用者核對，不直接寫成已確認店家。

【建議】資訊須分開保存：使用者輸入名稱、查得的名稱與別名、店家身分／分店、地址、座標、來源及查詢時間。人工更正不得被後續 AI 搜尋覆蓋；確認某家店不等於座標已確認。

【建議】驗收必須加入：只有中文譯名而沒有當地名稱；錯字／近似音譯；同名不同分店；地圖服務完全沒有回傳結果仍能完成「AI 查證 → 提出日期 → 確認排入 → Today」；多語來源互相矛盾時不強行合併。實際搜尋能力與來源可用性需用真實樣本驗證。

## 1.3 AI 提案、修改與暫緩

【已確認規格】產品負責人採用 Q04–Q06：

| ID | 已採用需求 |
|---|---|
| Q04 多筆提案與部分接受 | 同一旅程的多筆待安排內容彙整成一份建議，每項列出日期、店家與理由；可以全部接受或只勾部分，只提交選定項目，未選項目保留。 |
| Q05 修改與影響預覽 | 使用者可直接要求換日期、換店或指定時段；AI 更新受影響安排，清楚列出新增、移動、移除的內容，再由使用者確認。固定事項不自動移動。 |
| Q06 暫緩與拒絕 | 「先收藏」保留待安排、不排入正式行程；「這趟不安排」停止在該旅程主動推薦該項目，使用者可以重新啟用。 |

【已確認規格】同一份提案可接受部分、要求部分修改，其餘先收藏，不要求整份接受或重來。未確認的修改不能連帶套用到已接受項目。

【建議】部分接受前，系統依實際勾選內容重算相依的插入位置及交通影響；若結果與預覽不同，先更新預覽再確認，不提交依賴未選站點的安排。正式行程版本已變更時重新核對，不覆蓋旅伴的新修改。

【需實測或決策】「先收藏」何時再次推薦、連續匯入的彙整時機、同一來源再次匯入如何沿用「這趟不安排」，以及提案同時被兩人處理的細節，於共通狀態與同步階段落定。

## 2. 名詞與資料關係

【建議】以下作為節點討論的共同定義，待確認後才落成資料契約。

| 名詞 | 使用者看到的意義 | 關係與限制 |
|---|---|---|
| Trip／旅程 | 一趟旅行及其日期、成員 | 共同資料以旅程為邊界；不因加好友就公開全部旅行 |
| Day／某天 | 旅程中的一天 | 今天頁可切換日期；非旅行當天也能預覽 |
| Stop／行程站點 | 某天確定要去的一站 | 保留日期、順序、時間、定位與固定狀態 |
| Saved／收藏 | 想去但未必已排入的地點 | 排入行程後保留來源關聯，顯示已排日期 |
| Shopping／購物 | 想買的商品與購買狀態 | 商品、候選店、安排日期、購買紀錄分開 |
| Route Match／順路建議 | 比較加入哪一天、哪個位置較合適 | AI 可依目標旅程與查得的地區／時段提出安排；精確增加時間才需要可信定位及路線資料 |
| AI 草稿 | 可核對、更正的辨識與安排結果 | 不等於正式旅程；取消不改正式行程 |

| T2 AI 解析 | 按每天拆出地點、順序與時間，保留原安排；缺漏先標示，不擅自補景點、未知時間或重排行程。 |
| T3 確認地點 | 集中處理同名店、分店及查不到的地點；明確項目一起核對即可。查不到仍可保留為待定位，稍後再補，不阻擋建立旅程；航班、訂位標為固定事項供確認。 |
| T4 建立 Trip | 顯示完整每日預覽，可修改、刪除、調整順序；按下「建立旅程」才正式保存。中途離開保留草稿。 |
| T5 Today | 建立後進入今天頁；旅行期間顯示當天，尚未出發則預覽第一天，也能切換日期。顯示行程、導航及當日待買商品。 |

【已確認規格】待定位站點不使用未確認座標計算路線或提供導航；固定事項保留時間約束。

【建議】補充例外處理：空文字提示補上；AI 等待／失敗保留原文並可重試；建立失敗保留草稿與確認結果；重送不建立重複旅程。

【已確認規格】Q25：旅行結束後預設最後一天，手動選定日期保留；日期時間依行程所在地顯示。

【需實測或決策】跨國與跨午夜的呈現細節於頁面規格落定。

【建議】最小驗收：一份多日文字含同名分店及訂位，能更正後建立；原日期、順序與固定時間保留；Today 與建立預覽一致；取消建立不產生正式旅程。

## 3.1 點開行程查看附近探索

【已確認規格】產品負責人新增需求：點擊某行程時，可以同時查看 AI 助理提供的附近熱門景點、美食與特殊事件。納入新版核心範圍；本輪在現有 spec／planning 中未找到可直接引用的同名舊規劃，不將記憶中的提案視為已採用細節。

【已確認規格】Q10：「某行程」以當天的一個站點解讀，例如點開一間餐廳或景點；先查看該站原本的時間、地址及關聯商品，再在同一詳情頁呈現附近探索，不要求切到另一個獨立搜尋流程。入口為單一站點，非整天或整趟。

【建議】AI 以該站已查證店家／街區與旅程日期為脈絡，搜尋附近景點、美食及期間限定活動、展覽、市集、節慶等。此處以行程站點為中心，不默認使用手機即時位置；無座標仍可依地址／街區搜尋，只有店家身份及區域都未知時才需要先補查。

【建議】每筆推薦顯示名稱、類型、推薦理由、所在地區、資料來源與查詢時間；有可靠交通依據才顯示時間或距離，僅同街區不得宣稱步行幾分鐘。「熱門」要有可說明依據，否則標為推薦候選，不編造熱度排名。

【已確認規格】Q11：特殊事件比對使用者預計到訪日期，不只搜尋現在正在發生的事；顯示活動期間、場地及可取得的開放／預約資訊。已結束或日期不符不當作當日可參加；時間未核實顯示待確認，不當成確定開放。來源無法讀取或彼此矛盾時說明限制。

【已確認規格】Q12：查到推薦後可「先收藏」或「請 AI 安排」；後者依整趟旅程判斷，可建議接在該站前後或改到其他天，不強塞當天。所有正式變更沿用 Q04–Q06 的部分接受、修改與確認流程，並沿用 Q07–Q09 避免重複站點與錯誤連帶刪除。

【建議】開啟站點先顯示已保存詳情與可用的既有探索結果；AI 搜尋顯示進行中、資料更新時間及重試。探索失敗不影響原行程查看。快取多久、再次開啟是否自動更新、AI 排隊與離線時的具體行為於共通狀態階段決定，不承諾即時回覆。

【已確認規格】Q10–Q12 已採用；特殊事件按期間限定活動解讀，不包含另需定義的治安／災害／交通警報。推薦需附理由、日期及來源。

【需實測或決策】推薦數量、搜尋更新頻率及快取策略待定；沒有座標仍可依查證過的地址／街區搜尋。

【建議】新增驗收：中文譯名站點、無地圖座標但有街區，仍能查到有來源的周邊候選；活動符合到訪日；當天已有固定訂位時不直接插入衝突安排；同一候選已收藏／已排時沿用既有項目；搜尋失敗仍能查看原站點。

## 3.2 雙語計程車卡

【已確認規格】點開同一個行程站點，可開啟計程車卡，直接出示給當地司機，說明想前往的位置。卡片同時提供當地語言與使用者看得懂的語言，請求語氣禮貌客氣；這是新版旅行使用的核心功能。

【建議】入口沿用站點詳情，與附近探索並列；點「計程車卡」展開便於出示的大字卡片。卡片只呈現本次目的地，不公開整趟行程、購物清單或旅伴資料。

| 區塊 | 建議內容 |
|---|---|
| 給司機看的請求 | 以目的地當地語言表達「您好，麻煩您載我到這裡，謝謝您。」的自然禮貌說法，不使用生硬命令或逐字直譯 |
| 目的地 | 已核對的當地店名／地名、分店與當地地址；有需要且有依據才補入口或地標 |
| 使用者對照 | 同一句請求的使用者語言、使用者熟悉的名稱及可讀地址對照；第一版預設繁體中文（Q14 已確認） |
| 輔助操作 | 大字出示、複製目的地文字；有可信定位時可外開地圖，不能要求地圖查詢成功才能使用卡片 |

【已確認規格】沿用已確認的店家身份、分店及地址來源；不得將中文譯名逐字翻譯後當成正式當地店名，也不能為了製卡補造地址或座標。沒有座標但已有可靠店名／地址，仍可製作文字卡。

【建議】當地語言依目的地建議，使用者可切換；多語地區不只依國家硬指定單一語言。AI 可翻譯禮貌請求，店家專名與地址以查得資料為準。正式名稱未知保留原始名稱，不偽造當地名稱。

【建議】店家或地址仍有歧義時，先由 AI 補查並核對；可看草稿但明示待確認，不把未知目的地當成可直接交給司機的完成卡片。此限制只影響可靠出示，不阻擋該站先排入行程。

【已確認規格】Q15：卡片生成後保存於裝置，已保存的卡片可離線出示，不必每次叫 AI 重翻譯。站點換店、換分店或更正地址後，更新／重新核對卡片，避免顯示舊目的地；無法更新時明示，不能無聲沿用舊卡。

【已確認規格】產品負責人採用 Q13–Q15：

- Q13：從站點詳情點開大字計程車卡，當地語言為主要內容，繁體中文對照在下方，方便出示給司機。
- Q14：依目的地建議當地語言並可手動切換；第一版使用者對照預設繁體中文。
- Q15：已生成的卡片保存於裝置，可離線出示；換店或改地址後需要更新，資訊未核實明示，不顯示成已確認目的地。

【需實測或決策】卡片更新觸發時機、離線與另一裝置修改目的地的衝突處理於共通狀態階段定稿。語音播放、車資估算與叫車服務不在這次需求中，不自動加入。

【建議】驗收：韓文／中文譯名店家能顯示查證過的當地店名與地址、自然禮貌請求及繁體中文對照；無座標仍可出示；離線可看已保存卡；改分店後不顯示舊目的地；地址未知時不造資料；共享站點的卡片不洩露其他私人內容。

【需實測或決策】一次分享多店的批次收藏細節與重複分享的來源合併操作細節尚待確認；身份處理原則由 Q07 確認；多筆安排可部分接受已由 Q04 確認。

【建議】最小驗收：分享一份兩家店的內容，確認歧義後一間只收藏、一間排入某天；路線未知時兩者仍可完成；原始來源可回查。

## 4.1 重複項目、共用站點與撤回

【已確認規格】產品負責人採用 Q07–Q09：

- Q07：明確相同的店家／商品提示已存在，可補充來源，不重複排入行程。不同分店、型號分開；不確定時不自動合併。
- Q08：同一天同一店的多件商品關聯同一站點；已有該店行程就沿用，也可明確另安排一次到訪。
- Q09：撤回安排保留收藏或待買商品，只解除所選排程；店家站點仍有其他商品或原行程用途時保留，無其他用途才詢問是否一起移除。

【需實測或決策】刪除收藏／商品本身與撤回排程不同；刪除對正式站點、購買紀錄、必備用品關聯的原則依 Q27，不再重問；具體呈現見 §8。身份判定與重送去重的技術契約於開發前落定。

## 5.1 購買清單與旅行必備用品清單

【已確認規格】產品負責人已採用 Q01–Q03；新版核心包含以下行為。不代表整份舊行李提案或本節其餘建議一併採用。

| ID | 已採用需求 |
|---|---|
| Q01 AI 必備用品建議 | 建立旅程後，AI 依目的地、天數與活動主動提出用品清單；使用者選用，也能自行新增、刪除。 |
| Q02 購買與打包聯動 | 從必備用品點「需要購買」連到購買清單，區分出發前／旅途中購買；「已購買」與「已裝好」各自勾選。出發前需要的物品不安排成旅途中才買。 |
| Q03 個人與共同用品 | 分「我的物品」與「共同物品」；個人預設私人，共同物品可指定誰買、誰帶，旅伴看得到共同進度。 |

【建議】沿用 Shopping 作為唯一購買清單；已有購買項目時優先關聯，不重複建立。數量與完成狀態依 Q16–Q18；刪除關聯原則依 Q27。

【建議】AI 顯示用品建議理由；行程變動時只提出必要補充，不補回已略過項目、不覆蓋人工清單或打包狀態。AI 等待或離線不阻擋手動整理與勾選。

【建議】共享前說明範圍；購買與攜帶可由不同人負責，AI 可建議分工但不自行替旅伴承諾。共同物品的編輯、指派與代勾權依 Q20–Q21。

【建議】AI 助理在出發準備摘要呈現待買、未裝好及共同物品未分工；入口層級依 Q31–Q32，細部排版於線框圖階段決定。系統推播仍未納入已確認範圍。

【需實測或決策】仍需確認：私人用品連到購買清單時的可見範圍，以及刪除或取消購買後的用品關聯；共同項目的編輯／指派／勾選原則依 Q20–Q21。天氣、航空及入境要求等時效資訊，只有查到可靠來源才引用，不能把一般 AI 建議當成正式規定。

【建議】驗收案例：建立旅行 → 取得並選用用品建議 → 缺少用品連到購買清單 → 購買後仍顯示未裝好 → 裝好後獨立勾選；共同用品能查看分工，私人用品不外露；重跑 AI 不復活已略過項目、不重設完成狀態。

【建議】既有 [行李清單提案](packing-checklist-proposal.md) 僅作細節參考。其「行李為支線、AI 與購物聯動排第二階段」的安排不自動套用新版，依 Q01–Q03 將 AI 用品建議與購買聯動納入新版核心後重新規劃；舊提案其他細節不自動採用。

## 5.2 購買數量與完成狀態（已採用）

【已確認規格】Q16：購買項目預設數量 1，可修改需求數量及已買數量；例如已買 2／需要 3，仍列為未買齊。買齊才完成，可更正或撤銷。

【建議】不要求每次記錄價格或收據。

【已確認規格】Q17：共同購買可記每位旅伴需要的數量，分開記錄買給誰與誰負責買；例如甲要 2、乙要 1，共需 3，由甲代買。這些需求在共同購買項目內可見，個人購買不強制分工。

【需實測或決策】各人已買數量的分配操作另定，不憑總量推測買給誰。

【已確認規格】Q18：必備用品可設數量，第一版採整項未裝好／已裝好；勾選表示該項所需數量均已裝好，可取消。增加所需數量時重設為未裝好並提示，避免把新增份數誤算已完成。購買與打包仍各自記錄，不因買齊而自動打包完成。

【已確認規格】Q16–Q18 已採用；共同購買可見範圍不授權公開連結的私人用品清單。

## 6.4 手動封存旅程

【已確認規格】旅程可由使用者手動封存；已結束的旅程不自動封存。封存後不佔主要旅程列表，保留日後取出查閱參考。AI、日期到期或背景作業都不能自行封存。

【已確認規格】封存、退出與刪除是不同動作：封存保留旅程資料及原有成員權限；退出是離開共同旅程；刪除是擁有者明確移除整趟旅程。僅為了清理主要版面時不需要退出或刪除。

【已確認規格】Q28：封存是每位成員自己的列表整理，各人可封存或取消封存，不影響其他旅伴的主要列表與操作權限。擁有者封存也不代表整團停止使用旅程。

【已確認規格】Q29：提供「已封存旅程」入口，可直接打開查閱行程、收藏、購買紀錄及本人有權查看的用品清單；「取消封存」才移回主要列表，單純查閱不自動取消封存。封存不凍結共同資料，其他成員的有效更新仍可看見；若之後遭撤權，不能憑封存繼續取得共同資料。

【已確認規格】Q30：對已封存旅程，不主動產生新的安排／用品／附近推薦，也不列為新匯入內容的預設目標；歷史已保存結果仍可看。使用者主動要求查詢、修改或指定該旅程時，才按既有權限與確認流程處理，不自行取消封存。

【已確認規格】Q28–Q30 已採用。

【需實測或決策】封存目前選中的旅程時如何切換、所有旅程皆封存時的空畫面，以及封存時已在執行的 AI 工作如何顯示，於頁面與背景狀態設計落定。

【建議】驗收：旅程日期結束但仍留主要列表；手動封存才移出；封存列表能查閱原資料；只查看不自動恢復；取消封存後回到主要列表且資料不重複；兩位成員的個人封存互不影響（Q28 已採用）。
