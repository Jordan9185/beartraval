# BeaRTravel 分享後整理：Travel Inbox 產品流程與規格提案

版本：提案 v0.3 · 2026-09-26  
狀態：【建議】尚未取代 [現行 MVP 規格](ios-ai-travel-companion-mvp-spec.md)，亦不代表功能已實作或驗收。
開發拆解與驗收門檻見[下一階段開發計畫](../planning/share-inbox-delivery-plan.md)。

## 1. 問題與目標

【已確認規格】目前 App 有 Share Extension、Saved、Shopping、Route Match；正式行程只能在使用者看過影響後確認變更。Saved 是地點、Shopping 是商品，兩者維持分開。無法定位的地點不參與路線計算，商品庫存未知時不得宣稱有貨。

【現況觀察】分享地點時，畫面要求當場搜尋並選一個地點、選旅程，再收藏或加入某天；分享商品時切換到另一個流程。主 App 的「待處理的分享」只顯示本機草稿，主要供未登入或無法連線時續辦。一篇含多間店與商品的貼文，還沒有可保存原文、逐項整理的共同流程；同一來源目前在 `save_place` 也只會連到一筆 Saved。

【建議】把分享動作定義為**分享即收下，AI 自動整理並補全可查證資訊，只有必要時才請使用者處理**。使用者不必在分享面板選旅程、選類別、搜尋店名或等待路線計算。核心成功情境是：

> 看到內容 → 分享到 BeaRTravel → App 自動收下與整理 → 地點、商品或可編輯行程模板自動出現 → 只有歧義或要改正式行程時才請使用者確認。

這是「分享後整理」的產品切入點；不是自動替使用者修改正式行程。

## 2. 使用者流程

### 2.1 快速收下

1. 使用者從 Threads、Instagram、Safari、地圖 App 或照片選「分享 → BeaRTravel」。Share Extension 讀到 payload 後**自動保存並結束**，不要求再選旅程、地點／商品類型或按第二次「儲存」；只有保存失敗才停留並提供重試。【建議】
2. 立即保存可取得的原始內容與分享時間；若主機 App 提供多張圖片，保留每張的順序與讀取結果。顯示「已收下，正在整理」後返回原 App。即使只有 URL，也保存 URL；不要把「拿不到貼文全文」當成無法保存。【建議】
3. 未登入或離線時先存 App Group 本機佇列；進主 App 登入／恢復連線後同步。未登入時收下的內容，登入後先讓使用者確認要匯入目前帳號；切換帳號時不可默默上傳到另一帳號。保存失敗需明確顯示並提供重試，不能假裝成功。【建議】
4. 同一個已保存的 URL 再分享時，回到既有 Inbox 來源並更新最近分享時間；不新增一張內容相同的待整理卡。【建議】

【需實測或決策】Threads、Instagram、TikTok、小紅書等來源實際交給 iOS 的資料型別、URL 是否可開、圖片是否可取得，須逐 App／版本真機採樣。只有 URL 且讀不到正文時，先保存連結並標示限制；截圖或補文字是使用者想進一步整理時的可選退路，不以提示打斷分享；不繞過登入牆。

### 2.2 背景整理與通知

【建議】由主 App／後端以持久化工作處理，畫面狀態依序為「已收下 → 辨識中 → 已自動整理／部分待確認／只能保存連結／辨識失敗」。離開 App 或服務逾時不會丟失來源，也不應重複扣 AI 用量。完成時顯示簡短成果，例如「已收下 4 個地點、1 件商品；2 間分店待確認」。已確定的項目不等人開 Inbox 才落入個人清單。

【需實測或決策】是否送系統通知由使用者選擇；P0 先以 App 內未處理數和列表狀態提醒即可。通知文案不得宣稱「順路」，除非已確認地點、選定旅程且路線成功計算。

### 2.2.1 AI 自動補全的範圍

【建議】使用者只需分享一次，後續由 App 自動依可取得的資料逐層處理，**不要求使用者先抄店名或截圖**：

1. **讀來源**：先用分享 payload 的文字、圖片、地圖連結或實際影片檔；若只有網頁／影片連結，僅讀取公開且可合法取得的頁面資訊。記錄究竟讀到原文、影片畫面，還是只有標題與連結。
2. **抽線索與辨識內容型態**：從文字、畫面字幕／招牌、語音等抽出地點、商品、型號、先後順序、日期／時段及「去這裡做什麼」。判斷來源是推薦清單、完整行程或混合內容；每項附原文片段或影片時間碼。AI 推論與來源直接寫出的內容分開標示。
3. **查證並補欄位**：以地圖資料核對店名、分店、地址與座標；商品規格、可能販售店、營業時間、價格等只有找到可追溯來源才填，並附來源與查詢時間。查不到的欄位保持「未知」，尤其不得推稱有庫存。
4. **自動歸檔**：可辨識且意圖明確的地點／商品，自動放入個人「想去／想吃／想買」；重複項只追加來源，不建立新項。若內容有行程結構，另產生可編輯行程模板；模板中的每個停靠點不因此全部灌進個人收藏。意圖不明或僅被順帶提及的項目留在來源詳情作候選。
5. **結合我的旅行**：自動建議 Trip、比對既有收藏／購物項目；能精確確認地點時才試算 Route Match。Trip 不確定就維持個人收藏，不跳出選擇框。地點歧義、無法取得內容或路線失敗時，保留結果並標明限制。
6. **交付結果**：Inbox 顯示「已產生 3 天行程模板、加入 1 件想買；2 間分店待確認」或「已自動收藏 3 個地點」這類可核對摘要，提供更正／撤銷。AI 不替使用者付款、宣稱庫存、選錯分店或直接更改正式行程。

【建議】補全結果的每個重要欄位都應能回查來源，並分成「來源直接提供」「外部資料查得」「AI 推測」「未知」。使用者更正後要保存更正，不因重試又被 AI 覆蓋。

【建議】自動化依操作影響分級：

| 操作 | 預設行為 |
|---|---|
| 保存來源、擷取線索、查證、去重 | 自動執行，失敗時保留已收到的資料。 |
| 加入**個人**想去／想吃／想買 | 名稱與意圖足夠明確時自動執行；附來源、可撤銷。只是順帶提及的項目留作候選。門檻須用真實樣本校準。 |
| 產生個人行程模板 | 內容有足夠行程線索時自動建立**草稿**；原文順序與 AI 建議分天分別標記，可任意調整或刪除。 |
| 推薦旅程與路線 | 自動計算有足夠證據的候選；不確定時顯示未知，不強迫選旅程。 |
| 選歧義分店、公開到共同清單、改正式行程、購買或標已購 | 由使用者明確執行；正式行程維持 proposal 與版本檢查。 |

### 2.2.2 影片裡的地點

【現況觀察】目前的分享檢查器遇到影音附件只讀檔名與大小，不保存影片；`ShareContent` 只整理 URL、文字與第一張圖片縮圖，現有辨識流程**不會觀看影片畫面或聽聲音**。Threads／IG 影片分享實際提供影片檔還是只有連結，真機矩陣尚無資料。

【建議】影片進 Inbox 時先顯示「收到影片檔」或「只收到影片連結」，讓使用者知道可分析的材料不同：

1. **取得影片檔**：在既定隱私設定允許的範圍內由主 App 自動處理，抽取帶時間碼的代表畫面；對字幕、招牌、菜單與地名做文字辨識，必要時辨識口語內容，再把各時間點的線索合併成多個地點候選。畫面中只閃過的店名可能被抽樣漏掉；使用者需要時才提供手選畫面補抓。Apple 提供從影片時間點產生影格、對圖片辨識文字及辨識錄音語音的 API；這只證明技術路徑可行，不代表能準確辨識每一家店。[AVFoundation 影格擷取](https://developer.apple.com/documentation/avfoundation/creating-images-from-a-video-asset)、[Vision 文字辨識](https://developer.apple.com/documentation/vision/vnrecognizetextrequest)、[Speech 錄音辨識](https://developer.apple.com/documentation/speech/sfspeechurlrecognitionrequest)。【建議】
2. **只取得影片 URL**：先保存連結與主機 App 提供的標題／文字；如果無法合法取得影片內容，狀態顯示「只收下連結，尚未讀到影片畫面」。截圖、從相簿選影片或手動輸入店名只放在來源詳情作可選操作，不在分享當下要求。不能聲稱已分析影片，也不嘗試繞過平台存取限制。【建議】
3. **只有街景或店面畫面，沒有可讀招牌／字幕／口語店名**：可提出「疑似地點」作為搜尋線索，但不能確認是哪家或哪個分店；需人確認地圖候選，確認前不算 Route Match。【建議】

【需實測或決策】影片長度、抽樣密度、處理時間、上傳與保存期限、行動數據成本及多語字幕／口語準確率，需要以真實旅遊影片驗證。P0 先保證影片連結／可得附件進 Inbox 與截圖補抓；自動影格與語音分析需在 payload 與品質測試過關後排入開發，不先承諾所有影片都能自動識別。

### 2.2.3 從他人的行程自動產生模板

【建議】分享的若是「大阪三天兩夜」文章、時間表、社群貼文或可讀取的旅遊影片，App 自動建立**個人行程模板草稿**，不要求分享當下選「行程」模式。內容同時有必買商品時，商品仍可自動進個人購物清單；影片或文章內單純經過的地點保留在模板，不一律加進收藏。

- **有明確 Day 1／Day 2、早午晚或時間**：保留來源說明的分天、順序、停留時間線索與原文位置。外部作者的日期、機票或訂位只作參考，不直接變成使用者的 Fixed Stop。【建議】
- **只有多個地點，沒有明確順序**：先建立「未分天」模板；AI 可以依區域與可計算的交通時間提出分天方案，但標記為「AI 建議」，不能說是原作者的路線。【建議】
- **影片畫面先後**：保留每個地點出現的時間碼；剪輯順序可能不是實際遊玩順序，除非旁白／字幕明確說明，不能直接當成行程順序。【建議】
- **查證與路線**：分店有歧義的 Stop 保留名稱並標「待定位」；只有確定地點才能計算路線。營業時間、休息日、交通時間查不到時留未知，不為了排滿一天編造數字。【已確認規格／建議】
- **套用**：模板可預覽、刪除／拖動 Stop、改天數與時段。選「建立新旅程」或「套用到現有旅程」時，先看新增與衝突清單；現有 Fixed Stop 不可被移動。使用者確認後才提交正式行程，並檢查旅程版本。【已確認規格／建議】

【需實測或決策】目前文字行程匯入已具解析、地點確認與建立 Trip 的流程，但沒有「分享後自動生成、可反覆編輯的模板」。多 Stop 套用既有旅程需要新的整批 proposal 與版本檢查。影片模板依賴實際取得可分析的畫面／語音；只收到無法讀取的影片 URL 時，最多依可取得的標題或文字產生**部分模板**，不能假裝看完影片。

### 2.3 只在需要時打開 Inbox

【建議】Inbox 是處理紀錄與例外的入口，**已自動整理的分享不要求使用者逐張打開**。每張來源卡顯示：平台／來源標題、分享時間、建議旅程或「未指定」、已自動歸檔數／模板天數、真正需要處理的歧義數。點進去後保留原文、URL、縮圖與「原文未取得」提示；下方顯示多個項目或行程模板入口。

每個候選項目顯示：

- 類型：地點、餐廳／咖啡廳、商品；同一項可同時有「想去這間店」與「想買這件商品」的關係。【建議】
- 辨識名稱與原文片段；AI 推測的「想去／想吃／想買／只是提及」可修改。【建議】
- 地點候選與地址；分店有歧義時選分店，不能自動挑一家。【已確認規格】
- 目的備註，例如「去 Hiroshima PARCO 買限定款」；未有可靠線索時留空，不自行補故事。【建議】
- 自動歸檔結果與原因，例如「已加入想吃」、「已在收藏，新增一個來源」；每項都有更正、撤銷、略過。只有分店歧義、商品規格不明等例外才顯示主要待辦動作。【建議】

【建議】不把「全選 → 加入收藏」當成正常流程；系統已自動保存高信心項目。多項更正或刪除可批次處理；失敗項仍留在 Inbox。批次不能直接修改正式行程。

### 2.4 旅程與路線

【建議】系統先依地點、日期與既有旅程自動建議 Trip；使用者可日後改選。**只有確定是哪個 Place 並有可用座標的地點**才能試算 Route Match；顯示最佳日、增加旅行時間、交通方式、可行性與資料時間。營業時間或停留時長不確定時，明列為未知。Trip 或分店不明時先保存在個人清單，不強迫當場選。

【已確認規格】「順路」是加入後增加的旅行時間，不是直線距離；服務算不出時顯示「無法估算」。固定行程不可由 AI 移動，加入正式行程須再開 proposal 讓人確認，版本過期須重新確認。

【建議】對一篇貼文的多個店家，摘要可寫「3 個地點可估算、1 個未定位」，但不要把每一個單點 `+N 分` 相加當成整組繞路時間。若建議一次安排多間，必須按**同一日、同一版本、整組候選一起重算**，並顯示每項及整組的結果；首版可只提供單項安排。

### 2.5 完成與回查

【建議】一張來源可以同時有行程模板、已自動收藏、已加入購物、待確認與略過的項目。能自動整理的部分完成後，就顯示已整理與少數例外數；原文和來源仍可從模板／收藏／商品詳細頁回查。略過只影響此項，不刪除原始來源。使用者可重新開啟來源、改旅程、更正或撤銷自動結果。

## 4. 資料與 AI 契約

### 4.1 最小資料關係【建議】

| 物件 | 用途與必要欄位 |
|---|---|
| `Capture` | 一次分享來源；owner、建立時間、平台、原始 URL／canonical URL、可得文字與多張圖片參照（含順序）、處理狀態、選定 trip（可空）。保存來源先於辨識。 |
| `CaptureItem` | 一篇來源拆出的多個項目；種類、原文片段／影片時間碼、名稱、意圖、使用者更正、解析信心、處理狀態、自動歸檔去向。保留順序。 |
| `PlaceResolution` | 某候選項目與 Place 的關係；候選分店、確認人／時間、證據。沒有確認就不能試算或寫正式 Stop。 |
| `ProductMention` | 商品名稱、規格／色號、與可能販售 Place 的關係及證據；「可能販售」與「庫存」分開記錄。 |
| `ItineraryTemplate` | 個人模板草稿；來源 Capture、標題、城市、建議天數、建立時間、狀態及可編輯版本，不等於正式 Trip。 |
| `TemplateDay`／`TemplateStop` | Day 順序、Stop 順序、日期／時段線索、停留時間線索、Place 或原始名稱、原文片段／影片時間碼、是否為 AI 推測；未定位 Stop 可保留，但不計路線。 |
| `SourceLink` | CaptureItem 連到既有 Saved 或 Shopping 的多對多關係；同一地點可有多個不同來源，不因去重丟掉原始理由。 |
| `Decision` | 系統自動歸檔或使用者更正、撤銷、略過、提案的事件；actor、理由、時間與操作結果，支援回復誤判。 |

【建議】Capture、自動整理出的個人 Saved／Shopping 和行程模板預設只屬分享者；AI 可私下建議關聯 Trip，但不自動把原文或候選項目公開給旅伴。使用者安排正式行程或明確送入共同清單時，旅伴才看得到相應結果與可分享的來源摘要。現有資料模型以 Trip 為中心，這項需要個人清單／模板儲存與 RLS 設計，不能直接把本機 `ShareDraft` 當跨裝置 Inbox。

### 4.2 辨識輸出【建議】

每次辨識回傳 `content_kind`（推薦清單／行程／混合／未知）、`items[]`，必要時另有 `template_days[]`。每項至少有 `kind`、`raw_span` 或影片時間碼、`display_name`、`intent`、`confidence`、`candidate_place_queries[]`、`product_variant`（如適用）及 `missing_fields[]`。模板 Stop 額外標示天數／順序／時段是「來源明示」還是「AI 建議」。模型只提出候選與推測；地點地址、座標、營業時間、售價與庫存要由可追溯資料來源或使用者確認，不能把模型文字當成查證結果。

【建議】流程是「擷取 payload → 去重來源 → 保留原文 → 解析多項 → 查地點候選 → 標記重複實體 → 自動歸檔明確項目 → 旅程匹配／可行的路線計算 → 將例外留待使用者處理」。每一步有獨立狀態和錯誤，任何後段失敗都不會刪掉來源。

### 4.3 去重與推薦次數【建議】

- **來源去重**：同一 canonical URL／相同圖片或文字內容的重複分享，合併為一張 Capture，保留最近分享紀錄。
- **實體去重**：以地圖供應商 Place ID 優先；其次比對名稱、座標、地址及分店。疑似同一家時提示合併，不以相近名稱直接合併。
- **商品去重**：品牌、型號、規格及色號都需要比對；「ReFa」與特定型號不能直接視為同一件。
- **個人推薦次數**：顯示「你保存的不同來源提到 4 次」，計算相異來源，不計同一 URL 的重複分享；它不是評分、可信度或實際人氣。

### 4.4 Sonnet 5 在管線中的角色【建議】

【現況觀察】目前文字行程解析、商品辨識及旅程問答的預設模型是 `claude-sonnet-5`。既有文字解析輸入需要已知 Trip 日期與時區，輸出是供人確認的草稿；商品辨識目前可讀文字與一張 JPEG。它們尚未實現「任意分享 → 多種類型整理 → 無日期行程模板」的共同流程。

【建議】Sonnet 5 負責理解文字、圖片／影片抽出的代表影格與轉錄文字，產生有來源片段、時間碼與不確定標記的結構化候選。官方文件列出 Sonnet 5 的視覺能力與圖片輸入；影片應先由 App 抽影格，聲音先轉成文字，再交給模型理解，不把社群影片 URL 或原始影片直接當成已被模型看過。[Sonnet 5 功能](https://platform.claude.com/docs/en/models/sonnet-5/migration-guide)、[Claude 圖片輸入](https://platform.claude.com/docs/en/build-with-claude/vision)

【建議】POI 身分、地址、營業時間、商品販售證據及路線時間分別由可追溯的資料源與路線服務提供；Sonnet 5 只提出待查的名稱、關係與安排方案。去重、權限、正式行程版本檢查由確定性程式處理。先用真實文字行程、影片影格、字幕與「只有連結」案例評測地點召回、錯誤分店、分天順序、虛構內容、延遲及每次分享成本，再決定自動歸檔門檻與影格抽樣量。【需實測或決策】

## 5. P0 範圍與切分

【建議】交付「快速收下 → 自動分類 → 個人收藏／購物／行程模板」閉環；文字行程模板先重用現有解析能力，影片內容解析需以實測決定自動化程度。

| 順序 | 交付 | 完成判定 |
|---|---|---|
| P0-1 | Share Extension 快速保存 Capture；主 App Inbox 列表、原文回查、離線草稿同步 | 分享只給 URL（含影片連結）、未登入、離線、關閉 Extension 後資料仍可恢復；重複分享不產生重複卡。 |
| P0-2 | 多地點／多商品解析、可追溯補全、自動加入個人 Saved／Shopping、例外處理與撤銷 | 一篇四間店的明確項目不需逐項點擊就出現在個人清單；分店歧義保留待確認；失敗項不消失。 |
| P0-3 | 分享行程文字後自動建立可編輯模板；辨識來源與 AI 建議的分天／順序 | 原文有 3 天就保留 3 天；沒有天數就先列未分天；使用者不須在分享面板選模式。 |
| P0-4 | 已確認地點的 Trip Match 與單項 Route Match；模板建立新 Trip 或套用既有 Trip 的預覽與確認 | 顯示新增、未知與 Fixed 衝突；舊 Trip 不被靜默覆蓋；按確認前不改正式行程。 |
| 驗證後排入 | 可取得影片檔時的影格／語音自動分析並產生模板 | 需先有真機影片 payload、抽取品質、處理時間與隱私測試；只取得不可讀 URL 時不承諾畫面辨識。 |
| 後續 | 整組最佳日優化、背景位置提醒、商品即時價格／庫存 | 須有獨立資料與實地驗證；不列入本輪閉環。 |

【建議】既有的單地點立即處理畫面可以暫時保留作快捷路徑，但分享的主要結果應是「已收下，正在自動整理」，不能因 AI、MapKit 或登入延遲而讓使用者以為分享失敗。自動影片辨識須先通過真機 payload 與品質測試；只收到無法讀取的連結時，仍能做到零額外操作的**保存**，無法保證零操作辨識畫面內容。

## 6. 驗收情境（提案）

| ID | 情境 | 預期 |
|---|---|---|
| SI-01 | IG 只給 URL，貼文內容不可讀 | URL 成功入 Inbox，標記「只收下連結」；不憑 URL 猜店家，也不跳出要求截圖的視窗。 |
| SI-02 | 分享含 4 家聖水洞店的文字 | 來源只建一張卡、拆 4 個候選；意圖與地點明確者自動進個人收藏；分店有歧義者保留待確認，可事後更正／略過。 |
| SI-03 | 分享「去 ReFa SHOP minamoa 買 ReFa TREATMENT IRON」 | 辨識商品、店家與「想買」關係；商品自動進個人 Shopping，分店歧義仍待確認，庫存未知。 |
| SI-04 | 同一 URL 分享兩次；另一 URL 提到同一家店 | 第一種不新增 Capture；第二種保留不同來源並連到同一 Saved，推薦次數按不同來源計。 |
| SI-05 | 店名有兩個分店或查不到地點 | 顯示候選或「未定位」；使用者確認前沒有順路分鐘，也不能加入正式 Stop。 |
| SI-06 | 使用者沒有 Trip、未登入或分享時離線 | 可保留待整理來源；恢復後可選 Trip、續辦，資料不重複或遺失；登入後由使用者確認匯入目前帳號。 |
| SI-07 | 一篇有三個明確項目、第四個分店不明 | 三個項目自動進個人清單；第四個保留待確認，整篇不因它而卡住。 |
| SI-08 | 路線服務失敗或 Trip 已被旅伴修改 | 顯示無法估算或過期，允許先收藏；正式行程需重新試算與確認。 |
| SI-09 | Viewer 分享內容並自動整理 | 個人結果可保存；共同 Saved／Shopping／正式行程仍不可由 Viewer 提交，服務端也拒絕。 |
| SI-10 | AI 辨識逾時、重試或回傳錯誤格式 | Capture 仍在；重試不建立重複項目或重複計費工作；畫面能顯示可操作的失敗原因。 |
| SI-11 | 分享含多張圖片的輪播內容 | 所有實際取得的圖片按原順序保存與顯示；缺圖需明示，不把第一張當成整篇內容。 |
| SI-12 | 分享一支地點只在影片中出現的影片 | 若取得影片檔且影片辨識功能已通過實測，系統自動處理並附畫面時間碼；分店歧義才請人確認。若只取得無法讀取的 URL，顯示「只收下連結」，可選擇補截圖或影片，不產生虛構地點。 |
| SI-13 | 使用者只在來源 App 按「分享 → BeaRTravel」後離開 | 無須選 Trip、類別或逐項按收藏；可辨識的地點／商品完成後出現在個人清單，來源與撤銷入口可回查。 |
| SI-14 | 分享一篇明列「Day 1／Day 2／Day 3」的旅遊行程 | 自動產生 3 天可編輯模板，保留來源順序與每個 Stop 的原文；其他人的日期／訂位不會直接變成我的 Fixed Stop。 |
| SI-15 | 分享沒有日期的旅遊影片，畫面依序出現 5 間店 | 可取得影片內容時保存每間店的時間碼，建立未分天模板與可辨識地點；影片剪輯先後不被宣稱為真實行程先後。 |
| SI-16 | 使用者將模板套到已有固定訂位的 Trip | 先顯示新增／待定位／時間衝突，固定訂位不移動；使用者調整並確認後才提交，版本過期重新確認。 |
| SI-17 | 分享的影片只有不可讀的連結，貼文標題寫「東京兩日遊」 | 保存來源與可得標題；最多建立標明「資訊不足」的部分模板，不虛構兩天停靠點。 |

## 7. 與目前實作的差距及待決策

【現況觀察】`ShareFlowView` 的 `ShareAnalysis` 只產生一個 `suggestedQuery`；`ShareFlowView` 只對一個選定地點算順路。`ProductImportView` 已可從文字／圖片抽多個商品，但它與地點解析分流，還沒有來源級的混合結果與逐項持久化。現有文字行程匯入會解析後讓使用者建立 Trip，尚無分享後可反覆調整的模板。`ShareDraftStore` 只存在 App Group，沒有跨裝置待整理狀態。現有 `save_place` 在同一 URL 已有 Saved 時會直接回既有那一筆，無法表達「同一篇貼文提到多間店」。

【需實測或決策】

1. Inbox 與自動歸檔結果是否採個人私有；建議預設個人私有，只有明確送入共同清單／正式行程才共享對應結果。
2. 無 Trip 時可否先收下；建議可以，因為瀏覽收藏通常發生在排定旅程之前。
3. 截圖／影片原檔保存位置、期限與雲端辨識設定；建議首次設定時說明並讓使用者選擇，之後依設定自動處理，不在每次分享時重複要求授權。服務端處理須有刪除期限。
4. P0 是否要系統通知；建議先只做 App 內狀態與未處理數。
5. 支援來源的真機 payload 矩陣及 AI 抽取品質基準；以 [分享 payload 矩陣](../research/share-payload-matrix.md) 補證據，不把目前的 Safari 模擬器結果當作 Threads／IG 真機結論。
6. 現有 Share Extension 與 App 間的登入、離線、失敗回復路徑，須做真機與弱網測試；本提案不是已驗收證據。
