# BeaRTravel 辨識到出發：完整使用流程與開發計畫

版本：v2 · 2026-09-26

範圍：文字、圖片、截圖與可讀的分享連結；影片內容辨識另列後續階段。

狀態：【建議】依 2026-09-26 真機回報重寫，尚非已完成或已驗收功能。
依據：[MVP 產品規格](../spec/ios-ai-travel-companion-mvp-spec.md)、[分享後整理提案](../spec/share-inbox-proposal.md)、[實作交接](../handoff/2026-09-26-travel-inbox-implementation.md)及使用者提供的 Threads 餐廳／商品截圖與真機回報。

## 1. 要解決的事

使用者只做一次分享、貼連結或選截圖。App 要把「看到的內容」變成能使用的餐廳、地點、商品或行程草稿，而不是停在 OCR 文字。使用者之後可以從同一筆結果查看店名、當地地址、來源，收藏、選日排入旅程、開地圖、給司機看。資訊不足時清楚留待確認，不讓錯誤文字先填入表單。

【已確認規格】正式旅程由使用者確認才改變；AI 不猜分店、不移動 Fixed Stop；未確認座標的地點不參與路線計算。收藏是地點、購物是商品；有店家線索不代表商品有販售或庫存。

【現況觀察】分享收件、AI 整理、韓國店家查找、個人與共同收藏、購物候選、行程模板、Route Match 已各自存在。畫面間的結果與主動作尚未串成一條路：收藏後只見「試算順路」或「補填地點」；有韓文地址但沒有 Apple 地圖座標時無法直接排到某天；已辨識資料有些頁面未沿用。這是本版的優先問題。

## 2. 一條使用者看得懂的路

```text
分享到 App／貼連結／選截圖
  → 立即收下來源，離開分享畫面
  → AI 讀文字與圖片，抽出地點、商品或多天行程
  → 查可回溯的店名、當地地址與候選；保留原圖、文字、來源
  → 自動放入個人收藏／想買，歧義項留「待確認」
  → 使用者有需要時，選旅程與日期並確認排入
  → 旅程／今天／地圖顯示相同結果；司機卡沿用同一店名與地址
```

【建議】「收藏」是記住想去的店，不表示已排日期；「排進旅程」表示使用者已選日期。排進旅程可有兩種狀態：**已定位**的停靠點可算路線；**待定位**的停靠點只保留店名與地址線索，清楚顯示「路線未估算」。有地址與有座標是兩件事，畫面不得把前者寫成「已定位」。

## 3. 畫面與動作

| 位置 | 第一眼要看見 | 主要動作 | 次要資訊 |
|---|---|---|---|
| 分享面板 | 已收下／尚在此裝置、可恢復的狀態 | 返回原 App | 不要求先選旅程、類別或分店。 |
| 辨識結果 | 原圖縮圖、辨識出的項目、當地店名、地址、狀態 | 地點「收藏」；商品「加入想買」；多天內容「看行程草稿」 | 原始 OCR、搜尋證據、換圖、其他候選收在展開區。AI 完成前不先填猜測的店名。 |
| 收藏列表 | 店名、當地地址或「待查地址」、是否已排入某天 | 尚未排程顯示「排進旅程」 | 個人與旅伴共同項目標明範圍；不把「想去」當排程。 |
| 收藏詳情 | 名稱、地址、定位狀態、來源 | 「排進旅程」或已安排時「查看第 N 天」 | 獨立「開地圖」「給司機看」；來源網頁放在查找依據，不混作店家選項。 |
| 選日期 | 預選目前旅程；顯示日期、當天已有停靠點 | 「確認排到這天」 | 有可算路線時顯示增加分鐘與衝突；不能算時明示「無法估算」。Fixed Stop 保持原位。 |
| 旅程／今天／地圖 | 同一停靠點、日期與定位狀態 | 待定位者「確認地點」；已定位者查看路線 | 待定位項不畫假圖釘、不給假分鐘；可查看收藏來源與地址。 |
| 購物列表／詳情 | 商品名稱、候選店家與地址、證據強弱 | 「加入想買」後可「安排購買」 | 只有具體店家才選日期；標明「可詢問」與「庫存未知」。 |
| 司機卡 | 當地語言店名、當地文字地址，足夠大的字 | 出示給司機 | 地址只來自查得線索時顯示核對提醒；缺地址就明說，不能用中文介面地址冒充韓文地址。 |

【建議】整條流程只保留三個使用者需要理解的動詞：**收藏／想買、排進旅程、確認地點**。已定位時「確認地點」消失；未定位仍可先選日期，但不能顯示順路時間。「試算順路」成為選日期頁的結果，不作為收藏列表上的主入口。

## 4. 辨識與地點證據

1. 【建議】先分清貼文中的**地區、料理／商品、店名、地址、作者意圖**。搜尋列的「聖水洞必買」、手機時間、互動數及留言不是店名。巢狀截圖要找主要內容區，不以最上方 OCR 文字作答案。
2. 【建議】模型提出候選；可回溯的公開網頁、招牌／包裝文字與地圖資料各記來源。顯示「找到的韓文店名與地址」時仍可標為線索。多分店列最多三個有地址的選項，讓人挑選；沒有可核對證據就保留原圖與待確認項。
3. 【已確認規格】只有使用者選定可定位的地圖地點，或可證明唯一相符的定位結果，才寫入 `place_id` 與座標。地址線索保存在 `address_hint`，不能由 AI 拼出座標。韓國外開 Naver／Kakao 用韓文店名與地址；Apple 地圖搜尋失敗仍可保留線索與排程意圖。
4. 【建議】同一辨識結果有一份可重用的資料：項目種類、原文名稱、韓文／日文名稱、當地地址、來源、候選、確認狀態、相關旅程。收藏列表、詳情、排程、地圖與司機卡讀同一份欄位；使用者更正優先於 AI 重跑。

## 5. 收藏與旅程的狀態契約

| 狀態 | 收藏頁 | 排入某天後 | 路線／地圖 |
|---|---|---|---|
| 只有貼文或 OCR，無可信店名 | 待確認，保留來源 | 先要求補店名，不猜店 | 不顯示座標與分鐘。 |
| 有店名與地址線索，無座標 | 顯示地址與「待定位」 | 使用者確認日期後建立 `pending_text` Stop，保留與收藏的關聯 | 顯示「已排第 N 天 · 路線未估算」；不畫定位點。 |
| 有已確認的地圖座標 | 顯示當地地址 | 選日期時提供可計算的順路資訊與衝突，確認後建立 resolved Stop | 路線可用才顯示 +N 分；服務無結果則顯示未知。 |
| 多個可能分店 | 顯示候選並要求挑選 | 可先保存為待定位文字，但不得自選某分店寫入 Place | 不把候選分店放到正式路線。 |

【建議】從收藏選「排進旅程」時只問必要項：若只有一趟可編輯旅程就預選；若有多趟才選旅程；預選 AI 建議日期但可改。送出前顯示店名、地址、日期、定位與路線狀態；最後由使用者按「確認排入」。完成後在收藏顯示「第 N 天」，點一下直達那天。重複按不建立第二筆 Stop。

【需實測或決策】現有 `commit_itinerary` 可新增 `pending_text` Stop，但它會整批替換某天 Stop；應提供專用、具 `client_op_id` 和 `expected_route_revision` 的原子操作，安全地新增單一收藏、保留既有順序與 Fixed Stop，並同步收藏狀態及關聯。若 revision 過期，重新載入當天並讓使用者再確認。`place_id` 之後確認成功，再更新該 Stop 與收藏；這一步不能覆寫其他 Trip 共用的 Place。

## 6. 商品與行程模板沿用同一套語言

【建議】商品辨識先得到商品，店家是可查的購買線索。共同購物清單與個人想買清單顯示同一商品與候選店；使用者挑選店家、日期後才建立 Purchase Stop。只有網頁提到店家時顯示「可詢問」，沒有明確販售證據或庫存時不能寫「買得到」。店家未定位時 Purchase Stop 仍為待定位，不參與路線。

【建議】「東京五天」或分享他人行程時先產生可編輯五天草稿；使用者明列的地點必須保留並按指定日期／順序放入，沒有指定日期才由 AI 建議。套用前列出新增數、待定位數、與既有固定行程衝突及可估路線；按「確認套用」後才變成旅程。影像中看不出的日期與影片剪輯順序不當成原作者的真實安排。

## 7. 開發順序與交付邊界

| 階段 | 要完成的閉環 | 主要工程工作 | 交付判定 |
|---|---|---|---|
| P0：資料與狀態一致 | 截圖 → AI 結果 → 收藏／購物 → 列表／詳情／司機卡 | 統一結果模型與地址優先序；個人與共同清單標示；辨識前空狀態；保留來源；避免 AI 結果加入後消失。 | 使用者給的餐廳、餅乾、香水、Aesop 截圖在各頁顯示同一名稱與已取得地址，無亂填時間或搜尋標題。 |
| P1：收藏排進旅程 | 收藏 → 選旅程與日期 → 確認 → 旅程／今天 | 單一入口、待定位 Stop、已定位 Route Match、資料關聯、冪等與版本衝突；加入後直達該天。 | 無 Apple 地圖座標的韓國餐廳可排第 N 天但不進路線；有座標者可看 detour；兩者都能回查收藏與地址。 |
| P2：商品與模板 | 想買 → 選店安排購買；短句／貼文 → 草稿 → 套用 | 商品店家證據與 Purchase Stop 狀態；指定地點保留；模板日期、重複、Fixed 與 revision。 | 商品未宣稱庫存；東京五天與指定想去點依使用者選的日期套用，未知點留待定位。 |
| P3：真機流程驗收 | 從分享 App 到兩支裝置的全程操作 | Threads／相簿 payload、斷線重送、跨裝置同步、錯誤分店與回退、韓國地圖／司機卡；視結果再調整入口。 | 真機錄下完整流程並逐情境核對；簽章 build、CI、雲端部署與人工驗收分開記錄。 |

影片若只有不可讀連結，P0 只保存來源並說明資訊不足。影片抽影格、字幕／語音與時間碼需另做來源可得性、品質、延遲與成本測試，通過後再排後續工作；不把未讀到的影片內容當成已辨識。

## 8. 必須用真實樣本驗收

| 樣本與情境 | 需要看到的結果 |
|---|---|
| Threads「聖水洞美食」搜尋頁與多則留言 | 不把搜尋標題、時間或互動數當店名；能拆多項，無法確定的項目待確認。 |
| 無垢屋人參雞截圖、帶韓文招牌的餐廳截圖 | 顯示候選韓文店名、地址與查找依據；收藏後地址留在列表、詳情及司機卡；未定位仍可排日期。 |
| 餅乾照片裡又有一張手機搜尋截圖 | 辨識產品與品牌，不把手機狀態列或搜尋框當購買地點；查店要有來源。 |
| LOE 香水、Aesop 與眼鏡店貼文 | 產品與店家分開，品牌門市不等於產品有貨；購物清單重開仍有候選店。 |
| 「我要去日本東京五天旅遊」及附想去點清單 | 依日期生五天草稿；明列地點不遺失；未指定的日期才由 AI 建議。 |
| 兩支手機／兩個旅伴同時操作 | 個人原文只給本人；共同清單同步；同一收藏排程不重複；過期修改提示重看。 |

【需實測或決策】以這些真實樣本做一次完整點擊檢查。每一情境要記錄「輸入內容、AI 結果、來源、最後保存欄位、各頁顯示、路線狀態、裝置畫面」；單元測試通過只表示規則生效，不能替代兩支手機的流程驗收。
