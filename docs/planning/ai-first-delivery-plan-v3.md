# AI 辨識與懶人整理：主線交付計畫 v3

日期：2026-09-27。產品依據：[已確認主軸](../spec/ai-first-product-direction.md)。現況基準：`d47fa99` 與[全 App 稽核 L01–L15](../review/2026-09-27-app-logic-audit.md)。

【已確認規格】優先完成「真實內容 → AI 正確整理 → 找得到結果 → 確認安排 → 旅行使用」。AI 辨識不是最後才改善的工作。每階段都要減少使用者整理負擔，同時保留人工確認與可恢復性。

【建議】以下是工程拆解；第一批 AJ-0／AJ-1 實作與證據見[最新交接](../handoff/2026-09-27-ai-first-implementation.md)，其餘尚未交付。不新增未批准的技術選型。不得把已存在的收件、辨識、排程程式重新算成新功能已交付，也不得將全部工作標成單純 UI 修改。

## 1. 開工與順序

| 工作包 | 可交付的使用者結果 | 主要改動位置 | 依賴／對應問題 | 新驗收 |
|---|---|---|---|---|
| AJ-0：樣本基線及可信度修正 | 可核對現在辨識的對錯，未知路線與 Fixed 不誤導 | AI 測試樣本、RouteMatch、DayPlan、MatchNumbers、商品選店顯示 | 不依賴新功能；L03、L04 | AIJ-02、07 |
| AJ-1：懶人收件到結果 | 無 Trip 也能收；一份混合分享自動整理，結果和例外找得到 | ShareExtension、InboxCaptureStore／Repository、InboxView、Saved／Shopping 入口、inbox-organize | 沿用現有管線；先建 AJ-0 基線 | AIJ-01～04 |
| AJ-2：整理結果到旅程 | 個人項目直接加入指定日，來源／地址保留，查店失敗不丟保存結果 | InboxPublishView、ImportFlow、Saved／Shopping 排程、RPC、資料關聯 | AJ-1；L05、L06、L12；共同狀態支援見下 | AIJ-05、07、09 |
| AJ-3：AI 建議安排 | 既有行程、收藏集合、短句都能產生可核對草稿並確認套用 | parse-import、行程模板、RouteMatch、確認預覽、AI 上下文 | AJ-2 的持久關聯與版本；L09、L15 | AIJ-06、07、12 |
| AJ-4：旅行使用與回頭修改 | 能改行程、整理商品、完成／撤銷購買、導航，跨頁及跨裝置一致 | StopEditing、TripStore、Root／Today／Map、Shopping、OfflineQueue、ProposalReview | 可用閉環不得等此包才允許基本撤回；L01、L02、L07～11、L13、L14 | AIJ-08～11 |

【建議】依序交付 AJ-0 → AJ-1 → AJ-2 → AJ-3 → AJ-4；這是產品交付順序，不表示底層支援必須拖到最後：

- AJ-2 驗收前就要具備共同 Trip／Day、過期請求保護、新 Trip 目錄更新，以及已排站點的基本移除／重排；否則不能宣稱加入流程可用。
- AJ-3 驗收前就要具備草稿修改、正確 Fixed 檢查、穩定提交預覽與取消清理。
- AJ-4 補齊完整人工編輯、離線恢復及兩裝置驗收。每包的主線至少需能撤回本包新增的操作。

【需實測或決策】真實樣本需逐一確認可取得的附件、正確店名／分店與預期商品；歷史對話提到的圖片不能代替可讀取的測試輸入。未取得樣本時先記缺口，不自行重建假圖片當真實證據。

## 2. 每包的最小工作

### AJ-0：基線與硬性規則

【建議】使用無垢屋／韓文招牌、餅乾巢狀截圖、LOE／Aesop、多商品／多店、Day 行程、「東京五天＋指定點」及只有不可讀連結的樣本。分別記錄輸入、預期、模型／版本、實際結果、來源及更正次數。

【已確認規格】零容忍的行為錯誤：猜分店寫入已確認座標、未知分鐘變 0、漏掉未定位 Fixed 的風險、無來源冒稱庫存、AI 未確認改正式旅程。以規則測試保護，再用真實樣本核對輸出。

### AJ-1：收件與整理

【建議】統一外部分享與 App 內輸入的結果語言；不要求先有 Trip。不推倒既有擴充功能，先補入口、狀態回饋、混合多項結果、人工更正與重試保護。成功結果直達個人清單；例外不阻塞同份來源中的其他明確項目。

【已確認規格】保存與辨識完成是兩件事。重送不遺失來源、不重複結果；不同分店／商品不能僅因同 URL 被誤合併。

### AJ-2：持久發布與排程關聯

【建議】保存「來源項目、使用者、目標 Trip、共同項目及 Stop」可回查關係。相同來源再次發布到同 Trip 回同一筆；重新排程與新的使用者意圖要分開，不能無限制沿用舊操作 ID。

【已確認規格】核心保存／排程與選用 AI 補查分離；後者失敗顯示「已保存，店家待補查」。確認前明示共同可見範圍，後端驗角色與版本。跨頁沿用名稱、當地地址、圖片可用狀態及來源，不要求再抄一次。

### AJ-3：建議到草稿

【建議】保留既有文字解析與短句建議，補上收藏／商品集合到建議草稿的缺口。以使用者日期、指定點、Fixed、已定位路線及店家來源為輸入，輸出可編輯建議及依據；正式提交使用獨立確認。

【已確認規格】未定位仍可建議某天，但不得寫最順路或假分鐘。AI 上下文需包含新版已選店家與待定位狀態。整趟正式行程不得因生成新建議而自動重排。

### AJ-4：完成與恢復

【建議】補齊已定位／待定位站的改日、時間、停留、順序、Fixed 人工修改、移除；商品改名／備註、移除、取消安排／換店。購買紀錄保留與刪除策略需在實作契約中寫清楚。

【已確認規格】今天能直接完成／撤銷購買；選定日期與地圖一致。離線操作需可見待送／成功／遭拒；下滑關閉、返回與準備中離開都不得留下無人處理的 proposal。

## 3. 實作前需落定的契約

以下是【建議】的工程設計要求；確切 schema／RPC 名稱於對應包開始時定稿，不在此冒稱已存在。

| 契約 | 必須保障 |
|---|---|
| 辨識結果及人工更正 | 原始來源可回查；人工 revision 優先；過期 AI attempt 不覆蓋；單項失敗不回滾整份保存 |
| 發布去重 | 來源項目 × 目標 Trip 的持久對應及權限；同篇多店／多商品不混合；兩裝置並發同結果 |
| 排程／移日／刪除 | 使用者確認的預覽與實際提交一致；驗所有受影響日期 revision；收藏、商品、Stop 關聯與 Fixed 一致 |
| Trip／Day 狀態 | 同一選擇來源；回應世代／取消保護；帳號切換、權限改變與刪除 Trip 清除過時畫面 |
| AI 與路線資料 | 名稱／地址線索／定位／來源分欄；未知不為 0；未定位 Fixed 不從約束消失 |
| 向後相容 | 新 RPC 參數預設值、舊簽名處理與 grants；已安裝舊 App 可繼續使用；必要 migration 先 dry run |

## 4. 驗證與交付

【已確認規格】每包記錄「已開發、已部署、已安裝、已實測、已驗收」各自的證據。只通過本機測試／CI 不等於完成使用者主線。

【建議】依改動跑相應 Swift、AI、SQL／並發及 UI 檢查；至少增加完整 RootView 路徑的跨頁測試，不只測假服務獨立畫面。發布前檢查 Release 與真機，特別是 SwiftUI 清單及分享面板。

【已確認規格】主線交付必須實測：保存一份真實內容 → 找到 AI 結果 → 必要更正 → 排指定日期 → 修改一次 → 今天／地圖找到同一項 → 導航或完成購買 → 撤銷／重新安排。補充斷線、重開、重送、兩裝置同日競態與 Viewer 拒絕。

【需實測或決策】先記正確／錯誤項目、人工更正與步數、結果可見時間、完成率和費用，再訂量化門檻；不得以挑選過的成功案例代替樣本集。所需真機 payload、模型搜尋品質、雲端實際行為尚未在本輪重驗。
