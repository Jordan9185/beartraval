# BeaRTravel 全 App 邏輯稽核

日期：2026-09-27。基準：`d47fa99f443561a3e60b5b64c5de16bc79a498bd`，分支 `claude/github-new-project-v1pk1b`。

原稽核階段只新增本報告；後續主軸調整另更新產品文件，未修改 App、資料庫、雲端服務或使用者資料。依據 `CLAUDE.md`、MVP 規格、技術決策、最新交接與目前程式；不以先前交接的「已完成」代替現況檢查。這不是整個 App 的真機驗收，也不是完整安全稽核。

## 判斷

目前已有不少能獨立運作的功能，但尚未形成可反覆調整、可恢復失敗的完整旅行流程。最影響使用的是：

1. **加入正式行程後缺少基本編輯能力**，已定位的站點甚至沒有移除入口。
2. **相同內容從不同入口進來，後續操作不同**：個人清單、共同清單、正式行程之間缺少清楚且持久的關聯。
3. **旅程、日期、載入結果沒有一致的狀態管理**，切頁／切旅程／弱網路會放大問題。
4. **路線未知與固定行程資訊不完整，仍可能得到過度肯定的呈現**。
5. **自動化測試集中在模型與個別畫面**，尚未驗證使用者從分享一路走到排程、調整、導航、完成購買的閉環。

不建議繼續逐個堆辨識按鈕。應先修好「收下 → 找得到 → 排進去 → 改得動 → 旅途中使用 → 完成／撤回」這條主線。

## 一、目前每條流程在哪裡斷開

| 使用者目的 | 現有流程 | 缺口 |
|---|---|---|
| 建立旅行 | 名稱／短句／行程文字 → AI 草稿 → 地點及 Fixed 確認 → 建立 | 建立後無完整行程編輯；匯入查到的地址線索未完整帶入正式資料 |
| 分享地點 | 分享擴充功能保存 → 雲端整理 → 我的收藏／候選 | 要排程得先找「加入旅伴清單」，沒有直接「加入這趟旅行」的連續操作 |
| App 內新增地點 | 收藏新增／截圖 → 直接共同收藏 | 與外部分享進個人清單不同；使用者必須理解兩套狀態 |
| 排收藏 | 共同收藏 → 選日 → 確認 → 正式 Stop | 定位後不能移除；尚在試算時可送出，預覽與實際插入位置有競態 |
| 分享商品 | 個人想買 → 加入共同購物 → AI 查店 | 商品已存入後查店失敗，整頁仍報加入失敗；重開重送可能重複 |
| 安排購買 | 網頁店家線索 → 選日排入待定位站，或 MapKit 選店 → 最佳日 → proposal | 兩路行為不同；後者空白日可顯示假「+0 分」；商品缺少基本修改／刪除 |
| 旅途中看路線 | 今天切日 → 看站點 → 地圖／外開導航 | 地圖未跟隨所選日；今天可買清單不能直接勾選或進商品 |
| 問 AI | 當前 Trip 上下文＋部分收藏的順路試算 → 回答／proposal | 新版未定位選店資訊沒有完整進 AI 上下文；範例問題超過目前能提供的商品路線資料 |
| 旅伴協作 | Realtime 事件 → 各畫面重新載入，RPC 檢查權限及版本 | 各頁持有不同清單與載入工作；切換競態、離線失敗回報尚不完整 |
| 分享行程模板 | 收件詳情 → 編輯模板 → 套用到新／既有 Trip | 結果停在 UUID，沒有前往旅程；從收藏收件匣建立後缺少統一通知各分頁 |

## 二、應先修正的缺陷與缺漏

P1：核心操作走不下去、可能誤導行程判斷或產生錯誤資料狀態。P2：流程不一致、恢復與回饋不足。以下「程式確認」表示已追到可達分支，不表示已在真機操作重現。

### L01／P1：已定位的正式站點不能移除，正式行程缺完整編輯

**程式確認。** `StopDetailView` 只有 `place == nil` 才呈現 `PendingStopActions`。已定位站點只有導航、司機卡、附近搜尋等操作。`StopEdit` 只有定位、改文字、移除，沒有改日期、順序、時間、停留與 Fixed 的操作；時間軸也沒有正式行程的排序入口。

- 情境：把餐廳排到第 1 天，確認定位後發現要刪除或改到第 2 天；目前找不到可完成操作的入口。購買站一旦定位，也無法藉由移除重選店家。
- 影響：使用者無法正常修正自己的行程。不能用「AI 不可移動 Fixed」限制使用者本人編輯；兩者是不同規則。
- 證據：`Features/TripViews.swift:583`、`Features/StopEditingViews.swift:57`、`AppCore/StopEditing.swift:4`。
- 修正驗收：Owner／Editor 可修改及移除已定位／待定位站點；改日時明確確認，保留來源與商品關聯；舊版本拒絕覆蓋。Fixed 的人工修改需明示，AI 不得自行變更。

### L02／P1：切換旅程時，舊請求可覆蓋新旅程資料

**程式確認的非同步競態，尚未做裝置弱網重現。** `TripStore.selectedTripID` 每次切換都另開載入工作。`reload` 在等待回應後直接指定 `snapshot`，沒有確認目前仍選著同一 Trip，也沒有取消／世代檢查。新旅程讀取失敗且沒有快取時，舊 snapshot 仍留著。

- 情境：A 載入較慢，切到 B 且 B 先完成，A 最後回來；選擇值是 B，畫面資料可回到 A。另一情境是切 B 失敗，畫面繼續顯示 A。
- 影響：看錯旅程，權限狀態與目前畫面也可能不同步。後端權限仍有保護，不能據此宣稱已越權。
- 證據：`Features/TripStore.swift:12`、`:79–105`。
- 修正驗收：只允許目前 Trip 的請求更新畫面；切換時同步處理資料、權限、訂閱、錯誤與快取；A/B 回應逆序不得串頁。

### L03／P1：商品選店把「沒有路線估值」顯示成「+0 分」

**以現有路線原始碼執行最小重現。** 空白日或只有未定位點的日子，matcher 會回可安排的位置，但 `addedTravelMinutes == nil`。商品選店頁卻使用 `?? 0`。

- 情境：空旅程新增商品 → 找店 → 列出各店最佳日；尚無 Base Route，卻可看到「最適合第 1 天：路程 +0 分」。
- 證據：`Features/ShoppingView.swift:534–541`、`AppCore/RouteMatch.swift:213–219`。
- 重現結果：實際估值 `nil`；畫面同一運算式顯示 `+0 分`。此外 `bestDay` 在無估值但無後續 Fixed，與有估值但可行性未知的比較中，會選前者；缺乏估值的日子不能被包裝為最順路。
- 修正驗收：未知一律顯示無法估算；「可排入」與「建議最佳日」分開；已知 0 分才可寫 0。

### L04／P1：未定位的 Fixed 被一併排除，可能宣稱「之後沒有固定行程」

**程式鏈確認，路線層最小重現通過。** `DayPlan.from` 把所有未定位站點濾掉，只保留被排除的數量；Fixed 時間約束也因此消失。`fixedCheck` 只掃剩下的已定位站點。

- 情境：已匯入一班固定時間的航班，或一間還沒定位的訂位餐廳；新增別的地點時，固定事件可能不參與可行性檢查。
- 證據：`AppCore/AppleMapKitProvider.swift:47–65`、`AppCore/RouteMatch.swift` 的 `fixedCheck`、`ShareCore/MatchNumbers.swift:20`。`SavedScheduleView` 雖提示固定站不移動，並未保留這些站的時間可行性。
- 最小重現：`excludedPendingCount = 1`、無可定位站點的輸入，得到 `fixedCheck = noFixedAfter`。結合前述轉換，固定未定位站正會進入此種輸入。
- 修正驗收：未知座標仍不算路線，但保留 Fixed 的時間與排序約束；無法驗證時顯示「有固定行程，無法判斷能否趕上」。

### L05／P1：個人項目發布不是完整交易，重開頁面重送可能重複

**程式及 SQL 契約確認。** `InboxPublishView` 先建立共同商品，再查 AI 店家並寫線索；任何後續失敗都顯示「加入失敗」。每次重開畫面產生新 `operationID`，沒有持久的「來源項目 × 目標 Trip」對應。商品 RPC 只按操作 ID 去重；未定位地點發布又刻意不帶 canonical URL，也沒有 place ID 可去重。

- 情境一：商品成功存入，AI 額度用完 → UI 說加入失敗；使用者返回重試，新增另一筆商品。
- 情境二：同一個未定位個人地點先後兩次加入同一旅程 → 新操作 ID，可能建立兩筆共同收藏。
- 證據：`Features/InboxView.swift:299`、`:345–376`；`20260924000007_shopping.sql:99–131`；`20260925000016_review_low_fixes.sql:338–408`。
- 修正驗收：以來源項目與 Trip 建持久發布關聯；核心保存成功就回報成功，補查店家另外顯示可重試；同頁重試、重開、兩裝置重送都取得同一筆。

### L06／P2：個人清單到正式旅程的主操作不清楚

**介面流程缺漏。** `PersonalInboxRow` 只有確認地點、加入個人清單、加入旅伴清單等操作；不能直接選旅程／日期排入。即使獨自旅行，也要先理解「旅伴清單」才能繼續。

- 證據：`Features/InboxView.swift:816–870`；對照 `Features/SavedView.swift:484–505`。
- 建議：保留個人／共同資料邊界，但對使用者提供「加入旅程」連續操作，選 Trip、選日期、確認後完成發布與排程；已加入則顯示目的地與前往入口。稽核時屬流程調整建議；其後已由新產品主軸採用，尚未完成實作。

### L07／P2：今天選的日期沒有帶到地圖

**程式確認。** 今天用本地 `dayIndex`，地圖每次使用 `snapshot.todayIndex()`。`requestedDayID` 也只由今天消費。

- 情境：收藏排到第 3 天 → 查看第 3 天 → 點地圖，圖層和新增位置又按實際今天／旅程第 1 天。
- 證據：`Features/TodayView.swift:16`、`:79–91`；`Features/TripMapView.swift:21`。
- 修正驗收：共享選定的 Trip／Day，地圖明示日期並跟隨；「回到今天」是明確動作。

### L08／P2：新建／加入／刪除旅程後，收藏與購物的旅程清單未統一更新

**程式確認的狀態缺口，是否每次顯現取決於分頁生命週期。** Root 只重新載入 TripStore。Saved 與 Shopping 各自保留 `trips`；收到新 preferredTripID 時，必須先在舊 `trips` 中找到才接受。回前景的工作主要更新內容，不刷新旅程目錄。

- 情境：先打開收藏／購物，再建立或加入另一趟旅程；仍可留在舊 Trip，或新 Trip 沒有出現在切換清單。
- 證據：`Features/RootView.swift:142–148`、`Features/SavedView.swift:181–191,231–241`、`Features/ShoppingView.swift:95–117`。
- 修正驗收：Trip 目錄、目前 Trip 與角色使用共同來源；建立、加入、刪除、成員資格變更後各頁收斂。

### L09／P2：收藏還在試算時可提交，確認位置不穩定

**程式確認的競態。** 確認鈕只禁用 submitting，計算中仍可按；結果完成後才替換 `matches` 並可能改預設日期。`submit` 讀當下的 match 決定前後站，尚未完成時等同排到尾端。

- 證據：`Features/SavedScheduleView.swift:78–80,100,144–173`。
- 情境：使用者按確認時看到仍在估算，同一時刻估算完成，操作可能採尾端或新插入點。行程版本鎖只能擋其他人改資料，無法保證本機確認內容一致。
- 修正驗收：確認畫面使用不可變的提交預覽；計算完成改變位置時需重新確認，或明示「不等試算，排到最後」。

### L10／P2：共同商品存入後沒有名稱修改／刪除入口

**程式與公開 RPC 確認。** 辨識草稿可改名；共同購物列表和詳情主要提供購買勾選、照片、找店與安排，沒有商品改名、備註編輯、刪除的完整操作；也未找到對應的正式修改／刪除商品 RPC。

- 影響：打錯字、不再想買、L05 產生的重複商品無法正常整理。已安排商品也缺清楚的取消／改日／換店入口。
- 證據：`Features/ShoppingView.swift` 的 `ShoppingListView`、`ShoppingItemDetailView`；`AppCore/Shopping.swift`；目前 migrations 的 shopping RPC。
- 修正驗收：能改名／備註、移除及取消安排；定義是否保留購買歷史、如何處理已連結 Purchase Stop；避免用標記已購買代替刪除。

### L11／P2：今天可買清單無法完成購買操作

**程式確認。** 「今天可買」只是文字列，沒有勾選、商品詳情或購物分頁跳轉。

- 證據：`Features/TodayView.swift:151–166`。MVP §3.2 要求勾選立即更新進度。
- 修正驗收：在旅途中可直接勾選及撤銷，旅伴同步；完成後待買提醒消失，購物歷史保留。

### L12／P2：匯入頁查到的地址／來源，未完整帶到正式站點

**程式確認。** 網頁候選只存在 `ConfirmPlacesView` 的 `webCandidates`；選候選只再次搜尋地圖。`commitDays` 只組 label、時間、Fixed 與可選 place，未包含查到的地址與來源關聯。

- 情境：匯入時 Apple 找不到韓國餐廳 → AI 已顯示韓文地址 → 保留名稱建立 → 到正式行程，這份地址不能由新 Stop 取回供司機卡使用。
- 證據：`Features/ImportFlowView.swift:334–359,504–524`；`AppCore/ConfirmPlaces.swift:196–212`；`Features/TripViews.swift:555–577`。
- 修正驗收：明確選定的店名／地址線索／來源隨 Stop 保存，未知座標仍不算路線；不能因完成建立而丟掉已供使用者核對的資訊。

### L13／P2：下滑關閉確認視窗，未撤回 proposal

**程式確認。** 點取消會 reject，embedded 畫面消失也會 reject；一般 sheet 下滑關閉時 `embedded == false`，沒有對應清理，也沒有禁用互動關閉。

- 證據：`Features/ProposalReviewView.swift:83–99`。
- 影響：留下未確認 proposal；不會因此自動改正式行程，但違反本專案離開確認頁需撤回的規則。
- 修正驗收：取消按鈕、返回、下滑、準備中離開皆撤回；避免請求在頁面關閉後才建立 proposal 而無人清理。

### L14／P2：離線契約未完成，伺服器拒絕的佇列操作消失但未通知

**程式確認。** 離線佇列只有收藏、想去、購買，沒有新增 Shopping，與 D6 不符。非暫時性拒絕會移除佇列項目並回傳 rejected，但主要 UI 呼叫忽略結果。

- 情境：離線新增商品直接失敗；離線勾選購買後，角色被改成 Viewer，恢復連線時被拒，使用者得不到「未同步成功」的可處理紀錄。
- 證據：`AppCore/OfflineQueue.swift:4–8,78–87`；`Features/SessionModel.swift:90–92`；`Features/ShoppingView.swift:319–350`；技術規劃 D6。
- 修正驗收：實作承諾的非行程離線操作；保留待送／成功／遭拒狀態，拒絕理由可見且可處理，不默默丟棄。

### L15／P2：AI 助手沒取得新版未定位選店資訊

**程式確認。** 新購買站把店名與當地地址存於商品 `scheduled_store_*`，Stop 可沒有 place ID；`ask-trip` 的 `planned_store` 只由 Place 查名稱，未使用這些欄位，候選來源也只讀舊 merchant 表。

- 情境：購物／今天看得到「已選某店」，問 AI 卻只得到已安排日期、沒有店名。這是上下文缺資料，不宜先歸因為模型理解差。
- 證據：`supabase/functions/ask-trip/index.ts:120–131`；`ai/trip-assistant/src/schema.ts`；migration 30／31。
- 修正驗收：AI 看見已選店名、地址線索、定位狀態及來源；區分安排詢問、可能販售、庫存未知。商品沒有順路試算時不可保證哪天最方便。

## 三、需明確定義的產品方向與已知限制

以下不混入「已重現 bug」：

- **住宿起訖（D9）**：目前模型與 UI 沒有此設定，雖 matcher 有 `allowEndpoints`，呼叫仍允許頭尾。技術規劃已明列待重新確認。若要用 App 做每日旅遊規劃，需要明確決定是否把出門與回飯店納入。
- **地圖線條**：目前是站點直線虛線，程式註解有說明，但 UI 稱「今日路線」。應明示是行程順序；是否顯示真實路線幾何是另外的實作範圍。
- **無法估算仍可排程**：收藏及網頁店家線索允許；proposal 遇到 unavailable 會擋住。應統一「路線未知不代表禁止使用者安排」的產品規則，同時保留 Fixed 未能驗證的警告。
- **收藏分類**：分類篩選只套共同收藏，個人收藏仍全數顯示，發布時一律用 `.place`；使用者難以理解 Eat／Cafe 對哪些資料有效。
- **模板完成後**：目前成功頁顯示旅程 UUID，應提供「查看旅程」並同步全域選擇。從不同收件匣入口完成新 Trip，更新行為需要一致。
- **AI 額度與等待**：收藏自動補查、商品辨識後查店、發布商品再查店，是多個觸發點。已有記憶體快取，但部分流程仍把選用的補查與保存耦合；應將「已保存」與「正在補資料」分開。
- **影片、兩裝置、韓國地圖實地品質**：仍是最新交接列出的限制，不能用本次靜態稽核宣稱驗收。

## 四、已有的保護應保留

- 權限在 RPC／RLS 檢查，不只靠隱藏按鈕。
- 正式行程寫入有 route revision 檢查；proposal stale 不自動再次確認。
- 分享先保存 App Group，未確認帳號歸屬時不直接上傳。
- 未定位地點不產生假座標；收藏排程與購買排程保留未知路線狀態。
- 收藏／商品分開，店面線索與庫存有明示區別。
- 模板套用由使用者確認，後端在交易內檢查日期版本及保留既有站點。

這些保護有明確程式與測試基礎。修正應沿用，不需要推倒重寫。

## 六、原稽核建議修正順序與交付標準

**主軸確認後更新**：下表保留稽核當下的缺陷排序。產品負責人其後確認懶人整理與 AI 辨識是核心，現行產品交付順序改按[計畫 v3](../planning/ai-first-delivery-plan-v3.md)：先驗真實辨識與整理閉環，並依賴補齊編輯、狀態及可信度。不得照舊表把 AI 品質延到最後；L01～L15 證據及缺口仍需處理。

| 順序 | 工作內容 | 完成標準 |
|---|---|---|
| 1 | 行程編輯與商品整理（L01、L10、L11） | 使用者能安排、改時間、改日、調序、移除、重選店、勾選／撤銷；資料關聯不斷 |
| 2 | 共用 Trip／Day／載入狀態（L02、L07、L08） | 建立／加入／刪除後五頁一致；切換與回應逆序不串資料 |
| 3 | 分享到旅程的持久關聯（L05、L06、L12） | 重試不重複，保存與補查分離，地址／來源跨頁一致，可直接看到排在哪天 |
| 4 | 路線與 Fixed 的可信度（L03、L04、L09、L13） | 未知不為 0、不假稱沒有 Fixed；按確認所見即所送，離開撤回 proposal |
| 5 | 離線恢復與 AI 上下文（L14、L15） | 使用者知道每筆是否已同步；AI 與畫面看到同一份已選店家資料 |

前三項是產品能否順暢使用的主線；L03、L04 的局部保護可先修，不需等待全部流程改造。

每項修正都要以端到端情境收尾：

1. **建立與修改**：建立兩日 Trip，加入已定位／待定位／Fixed 站，改時間、改日、重排、移除，重開後結果一致。
2. **分享地點**：Threads URL 與純圖片各一筆 → 可見辨識狀態 → 核對 → 排第 2 天 → 今天／地圖／司機卡一致 → 移除後可重排。
3. **分享商品**：多商品圖 → 核對 → 加入旅程 → 選店 → 安排 → 勾選／撤銷 → 改店；每步能回頭。
4. **失敗恢復**：核心保存成功但 AI 查店失敗、送出逾時、關閉再開、重複點擊、兩裝置同時提交，資料不重複也不遺失。
5. **旅程與日期切換**：A/B 快速切換、先後回應逆序、新建／刪除 Trip、從收藏跳指定日期，所有分頁一致。
6. **真實未知路線**：韓國不支援的交通方式、空白日、含未定位固定航班、弱網；不得顯示假 0 分或錯誤保證。
7. **協作／離線**：另一裝置修改、Viewer、離線勾選後被撤權，版本衝突及拒絕都有明確結果。
